# Адаптер дневников БАРС

Контракт реализации FillBARS 5.2.5. Привязки получены при диагностике интерфейса БАРС 07.09.2026; последовательное сохранение двух дневников и содержимое записей затем проверены врачом в этой установке МИС. Совместимость с другими учреждениями и изменёнными шаблонами требует отдельной проверки.

Документ содержит только структуру интерфейса, без реквизитов пациентов и содержимого медицинских записей. Руководство пользователя: [дневники врача](diaries.md).

## Разделение модулей

- `diary-core.js` — модель строки и очереди, даты, библиотека вариантов, пары слов, настройки и проверки. Формат библиотеки — версия 3 с чтением версий 1 и 2.
- `diaries.js` — редактор, предпросмотр, библиотека, подтверждения и отображение состояния.
- `diary-background.js` — последовательная очередь, разрешённые команды, состояние в `chrome.storage.session` и настройки в `chrome.storage.local`.
- `diary-bars-adapter.js` — чтение контекста и действия в конкретной форме БАРС через `chrome.scripting` в мире `MAIN`.
- `diary-window.js` — единственное окно дневников; повторное открытие фокусирует его.

Разрешения расширения: `activeTab`, `scripting`, `storage`. Постоянные разрешения на все сайты не добавлены. Модуль использует открытую авторизованную вкладку; самостоятельного API-клиента, доступа к базе и криптоключу нет.

## Контекст пациента и приёма

Карточка определяется как единственная видимая `.hosp_history_new`. Из неё читаются `PAT_FIO`, `PAT_BDATE`, `HH_PREF_NUMB`. Локальный ключ контекста состоит из нормализованных ФИО, даты рождения и истории болезни. Это проверка отображаемого контекста, а не идентификатор серверной сущности. Перед подготовкой, сохранением и подтверждением результата контекст перечитывается.

Корень редактора:

```css
[cmptype="Form"][formname="UniversalTemplate/UniversalTemplate"]
```

Сам по себе этот универсальный контейнер недостаточен. Дополнительно проверяются:

- единственный видимый экземпляр редактора;
- услуга `Ctrl_SERVICE` с точной подписью «Дневник врача»;
- выбранный случай `Ctrl_DISEASECASES`, содержащий историю болезни открытой карточки;
- ФИО в заголовке «Добавление приема» вне содержимого самой формы;
- полный и однозначный набор девяти доступных полей.

Заголовок «Редактирование приема» не разрешает использовать существующую запись как новую. Текст унаследованного дневника не используется для установления пациента. Отображаемые значения читаются из самого `input`, вложенного видимого поля либо выбранного пункта `select`; скрытые ID не подменяют подписи.

Новое окно может появиться раньше услуги, истории болезни и полей. Адаптер ожидает готовность и стабильность значений в течение 700 мс; предел одного ожидания — 18 секунд. Числовой ID экземпляра окна не фиксируется.

## Поля

Основная привязка — `template_field` внутри проверенного редактора. Числовые имена в таблице приведены как наблюдение текущего шаблона; адаптер не фиксирует их как универсальные селекторы.

| Назначение | `template_field` | Наблюдавшееся имя | Целевой элемент |
| --- | --- | --- | --- |
| Дата осмотра | `VISIT_DATE` | `82638108` | `input` |
| Время | `VISIT_TIME` | `82638107` | `input` |
| Температура | `TEMPERATURE` | `82638115` | `input` |
| АД | `AD` | `82638118` | `input` |
| ЧСС | `THSS` | `82638117` | `input` |
| ЧД | `THD` | `82638116` | `input` |
| Дневник | `S_DNEVNIK` | `82638119_Text` | `textarea` |
| План обследования | `STAC_PLAN` | `82626435_Text` | `textarea` |
| План лечения | `RECOMEND_CONS` | `82626456_Text` | `textarea` |

У `FillingTextArea` используются итоговые текстовые области, а не поля поиска стандартных текстов. Имя словаря плана лечения `STAC_HPLAN` отличается от `template_field="RECOMEND_CONS"`. Рекомендации входят в план лечения; четвёртого текстового поля нет.

Все девять значений заменяются явно, включая пустые планы. При наличии API формы используется её `setValue` в контексте страницы; при необходимости значение точно заменяется штатным setter элемента. Затем отправляются события `input`, `change`, `blur` и перечитываются поля. При позднем наследовании допускается до трёх попыток замены до сохранения. Непринятые значения останавливают подготовку.

Показатели передаются как свободный текст до 67 символов, каждый из трёх текстов — до 4000 символов. АД не разбирается на числа при записи. Проверка числовых значений и соотношения давления применяется только к учебному генератору. Дата и время проходят календарную проверку; будущее время допускается.

## Открытие и сохранение

Путь: карточка → «Осмотры» → «Провести осмотр» → двойное нажатие строки услуги «Дневник врача» → готовый новый приём.

Штатные кнопки редактора:

| Кнопка | Имя | Наблюдавшийся обработчик |
| --- | --- | --- |
| Применить | `Btn_Save` | `base().SaveContinue()` |
| Сохранить | `Btn_SaveClose` | `base().Save()` |

Адаптер нажимает `Btn_SaveClose` внутри проверенного окна. Прямые серверные запросы не создаются. Перед нажатием повторно сверяются контекст и девять значений. Этап отправки сохраняется в состоянии фоновой очереди до вызова адаптера.

Список осмотров — видимый `GRID_DIRECTION_OBSERVATIONS` с `cmptype="Grid"`. Строки `GridRow` читаются по `keyvalue` или вложенному `item_value`. Идентификатор используется только для различения наблюдаемых строк; его серверная сущность не предполагается.

Успешное сохранение подтверждается закрытием редактора и появлением новой строки с новым ID, услугой «Дневник врача», датой и временем текущей записи. В журнале это обозначается `verification: "list"`. Закрытия окна самого по себе недостаточно. Содержимое сохранённой записи повторно не открывается и не сравнивается; серверное преобразование текста этим способом не исключается.

Перед подготовкой также проверяется отсутствие дневника с теми же датой и временем в видимых строках. Эта проверка не охватывает другие страницы списка и не является серверным ограничением уникальности.

## Прерывание и продолжение

Очередь работает последовательно в исходном документе и фрейме. Результат каждой записи хранится с её локальным ID. Подтверждённые строки пропускаются при продолжении и блокируются от повторного редактирования и отправки в текущем черновике.

Если сохранение вызвано, но не подтверждено, состояние — `uncertain`. После перезапуска service worker незавершённый этап `saving` тоже становится неопределённым; другие незавершённые этапы — `interrupted`. Автоматического повторного сохранения нет.

Команда ручного продолжения проверяет ID очереди, текущую строку и пациента. После подтверждения врачом сначала сохраняется результат записи, затем освобождается состояние адаптера и запускается оставшаяся часть очереди. Двойное нажатие обрабатывается последовательно. Ручной результат помечается `verification: "manual"`, а не выдаётся за автоматическую сверку.

Демонстрационные и непроверенные записи отклоняются фоновым обработчиком. Команды принимаются только от страниц самого расширения; исходная страница БАРС не может запускать очередь сообщением от своего имени.

## Хранение и диагностика

`chrome.storage.local` содержит настройки и библиотеку шаблонов. `chrome.storage.session` содержит привязку вкладки, реквизиты пациента, черновики, состояние очереди и отметки отправки. Состояние переживает закрытие окна и остановку service worker, но не перезагрузку расширения и завершение сеанса браузера.

Экспорт журнала содержит до 250 технических событий последнего запуска: этап, порядковый номер записи, результат проверки и код причины. В экспорт не включаются ФИО, история болезни, дата рождения, тексты, показатели и ID медицинских записей. Само состояние очереди целиком не экспортируется.

## Проверки

Команды из корня проекта:

```sh
npm ci --ignore-scripts
npm test
npm run check
npm run test:upstream
```

Тесты используют `jsdom`, искусственную структуру БАРС и подменённые API расширения. Покрыты задержанная загрузка и наследование, полная замена полей, подтверждение по списку, ручное продолжение без дубля, смена пациента, прерывание worker, свободные показатели, шаблоны, род и единственное окно.

Проверки другой установки БАРС должны включать фактическое открытие сохранённых дневников и сверку полей. Работа с другой услугой или структурой редактора требует отдельного контракта, а не отключения проверок текущего адаптера.

# Фоновое сохранение дневников: исследование протокола

Дата: 16.09.2026. Статус: реализован и проверен тестовый фоновый адаптер; ниже сохранены результаты исследования протокола.

## Проверено в открытой сессии

Через браузерный CDP прочитаны загруженные `system.1787138386.js`, `d3/~d3api` и сценарий открытой формы. Запросы создания или сохранения исследователь не отправлял. Ключи, cookies и значения авторизации не извлекались. Документ не содержит реквизитов пациентов и текстов дневников.

- Рабочий список использует D3: `ArmPatientsInDep/pat_in_dep/healing_emp_d3`.
- Карточка: `ArmPatientsInDep/hosp_history_new`.
- Промежуточная форма: `ArmPatientsInDep/Wrappers/direction_observations`.
- Редактор дневника использует legacy DForm: `UniversalTemplate/UniversalTemplate`.
- В исследованной форме режим `INSERT`, идентификатор визита ещё отсутствует, направление и случай уже заданы. Сам факт наличия направления не доказывает, когда оно было создано.
- Параметры формы имеют ключи `service`, `template_id`, `modal`.

## Последовательность сохранения по исходному коду

`Save()` вызывает `BeforeSaveVisit(true)`, затем `runSaveInSynchronousMode(0)`. Дата и время объединяются в переменную даты визита. Затем выполняются `checkBeforeVisitSave()` и последовательная цепочка `checksBeforeSaveArray`.

В цепочке присутствуют серверные проверки, условные ветки и подтверждения пользователя. Пример обязательного вызова: `CHECK_BEFORE_VISIT_SAVE_ACTION`. Проверки льгот, диагнозов, прав, контрольных карт и выбора случая нельзя считать отключёнными только потому, что это дневник. В исследованной форме `CHECK_PRIV_GROUP_BEFORE_SAVE = 1`, `CHECK_ANALYZE_BEFORE_SAVE = 8`; ряд других проверок имеет значение 0.

`FillAction()` группирует `FILL_ACTION` и `LAST_FILL_ACTION` через `startActionsGroup(0, true)` / `endActionsGroup`. Комментарий БАРС указывает на выполнение группы в одной транзакции. Проксирование этих двух действий через Fetch в открытой форме выключено. Массивы дополнительных действий перед/между ними пусты, но `AfterSaveVisit` содержит обработчик. После сохранения предусмотрены дополнительные проверки и возможное формирование ЭМД.

## Транспорт

Для legacy DForm `requestServerMultiActions()` формирует POST к `getmultiaction.php` с `Form`, параметрами формы и параметрами кэша/темы. В теле используются `act0[Form]`, `act0[Action]`, `act0[_sysid]` и параметры первого действия; далее `act1[...]`. Тип тела: `application/x-www-form-urlencoded; charset=UTF-8`.

Ответ разбирается как XML `multidata` / `actiondata`. Проверяются ошибки действий, затем вызываются обработчики результатов. HTTP 200 сам по себе не подтверждает сохранение.

Отдельно D3 использует `request.php` и JSON в поле `request`; это не означает, что дневник сохраняется тем же протоколом.

## Состав данных

В `FILL_ACTION` 48 входных параметров с суффиксами `_g0` ... `_g47`, а также выходные и серверные session-параметры. Суффиксы относятся к конкретному сгенерированному шаблону и не должны считаться универсальными.

Кроме девяти полей FillBARS передаются связи с пациентом, направлением, случаем, услугой и исполнителем, параметры закрытия случая и другие значения. В текущем шаблоне также присутствуют `MIDWIFE`, `SOVM`, `DOM`, `INFO`, `VISIT_PURPOSE`, `SOVZAV`, `STAC_PROV`, `STAC_PROV_A`. Наличие поля на форме не означает, что оно является прямым параметром `FILL_ACTION`.

## Что ещё необходимо установить

1. Фактическую последовательность запросов одного штатного сохранения и формат успешного ответа, без повторного воспроизведения записи.
2. Получение нового контекста направления и шаблона без открытия редактора: нельзя повторно использовать идентификаторы уже сохранённого визита.
3. Полный набор применимых проверок и обработку веток, требующих решения врача.
4. Чтение сохранённого результата и сверку полей; остановку без автоматического повтора при неопределённом результате.
5. Проверку фонового адаптера на изолированных фикстурах и отдельную ручную проверку врачом. Сетевые записи нельзя включать в публичные артефакты с персональными данными или авторизацией.

До установления этих пунктов замена адаптера простым вызовом `FILL_ACTION` не обеспечивает эквивалентность штатному сохранению.

Присутствие ключа доказывает передачу поля, но не точное содержимое: значения намеренно не записывались.

После группы наблюдались `getMkbCode`, `checkVimisAkineo`, `checkIKBR`, `checkSpepEris`, `checkEmergNotify`, `deleteDirectionObservationsAfterVisit` и обновление набора данных. Название последнего действия не следует понимать как разрешение удалить осмотр: оно входит в штатный обработчик закрытия формы, его серверная семантика отдельно не установлена.

Все перечисленные запросы получили HTTP 200. Корень ответа группы — `multidata`, XML разобран без parsererror. Временный регистратор не сохранил исходный XML и не обнаружил дочерние `actiondata`; поэтому эта запись **не устанавливает** формат возвращаемого ID визита и не доказывает отсутствие ошибок внутри действий. Сверка текста сохранённой записи пока не выполнена. Повторно воспроизводить записанный запрос нельзя.

По коду wrapper новый вызов `execDirectionObservations` получает контекст направления перед открытием редактора. Он также может потребовать выбора подуслуг (`NEED_SUB_SERVS`). Следовательно, для полноценного фонового клиента недостаточно повторно использовать контекст последней открытой формы.

## Реализованный тестовый режим 16.09.2026

В сборке `background test 3` рабочий iframe размещён внутри отдельного скрытого родителя. Причина: штатный `D3Api.DLoading` из iframe вызывает `window.parent.document.querySelector('spinner-ctrl').show()/hide()`. Частный родитель изолирует оба вызова с начала загрузки, не затрагивая индикатор ручных запросов основной карточки. Живая проверка загрузки карточки и штатного DLoading: 0 вызовов основного индикатора. Пользователь подтвердил исправление. Пройдены 127 локальных тестов; одновременные серверные записи разных типов пока не реализованы.

Пользователь разрешил скрытый контекст при условии отсутствия видимых окон. Добавлен `diary-hidden-adapter.js`: same-origin iframe в исходной вкладке, штатная карточка через `openWindow`, затем существующий адаптер форм с проверкой исходного пациента. Параметры `HH_ID`, `HH_DEP_ID` и необязательный `HH_VIEW_MODE` читаются из открытой карточки и передаются объектом из realm фрейма (БАРС использует instanceof). `PATIENT_ID` может ещё отсутствовать в свежей карточке и не передаётся: его инициализирует штатный процесс БАРС. Ключи ЭП и cookies не копируются; действует текущая сессия браузера.

Подготовка загружает только карточку. Создание направления и сохранение начинаются после устойчивого checkpoint `saving`. Ошибка после начала этой стадии блокирует повтор до ручной проверки. Успех определяется новой строкой списка, не повторным чтением сохранённого текста. После успеха фрейм удаляется. При неопределённом результате он остаётся скрытым до явного разбора операции. Дополнительные диалоги не подтверждаются автоматически; iframe sandbox запрещает native modal, popup и верхнюю навигацию. Видимое «Заполнить в окне без сохранения» сохранено как отдельный ручной режим.

Живая проверка в текущем Яндекс Браузере: готовый адаптер создал один скрытый фрейм, прочитал ту же карточку, не создал редактор UniversalTemplate и удалил фрейм по release. Исходная карточка осталась одна. Сохранение в рабочую карту агент не запускал. Полный цикл проверяется на искусственном DOM; фактическое сохранение и семантику результата проверяет врач на тесте. Исходный список осмотров может потребовать ручного обновления. Пока очередь работает, исходную вкладку и карточку необходимо оставить открытыми.
